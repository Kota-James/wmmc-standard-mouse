# 開発運用 Tips — リポジトリ衛生・デバッグ・その他知見

本編 4 文書に収まらないが改修時に役立つ情報をまとめる。

## 1. リポジトリ衛生（今回の改修で最初にやるべきこと）

### 1.1 文字コード・改行コード
- `main.c` は過去の文字コード変換失敗でコメントが文字化けしている（U+FFFD 混入）。
  中身は他ファイルのコメントや git 履歴から復元できないため**書き直し**になる
- 全ファイルを UTF-8 / LF に統一し、以下を置く:

```gitattributes
# .gitattributes
*.c text eol=lf working-tree-encoding=UTF-8
*.h text eol=lf working-tree-encoding=UTF-8
*.md text eol=lf
```

```editorconfig
# .editorconfig
root = true
[*.{c,h,cpp,hpp}]
charset = utf-8
end_of_line = lf
indent_style = space
indent_size = 4
```

- CubeIDE 側も Window → Preferences → General → Workspace で
  Text file encoding を UTF-8 に設定させる（新入生の環境構築手順に入れる）

### 1.2 フォーマッタ
- 一部ファイルは過去に clang-format がかけられ、日本語コメントが不自然に
  折り返されている（`search.c:61-63` の `route\n[r_cnt++]` 等）
- `.clang-format` をリポジトリに置き、`ReflowComments: false` と
  `ColumnLimit: 100` 程度にすると日本語コメントの破壊を防げる
- 「フォーマットは機械に任せ、レビューでは指摘しない」を部の文化にする

### 1.3 .gitignore / ブランチ運用
- `Debug/`（ビルド生成物）は commit しない（設定済み）
- `.ioc`, `.cproject`, `.project`, リンカスクリプトは**管理対象**（環境再現に必須）
- ブランチ運用の詳細は [02_教育向け再構成案.md](02_教育向け再構成案.md) §5 参照

## 2. デバッグ手法（新入生に最初に教える価値が高い順）

1. **printf（UART, 115200bps）**: 現行環境で既に使える。Tera Term / CubeIDE 内蔵
   ターミナルで見る。ISR 内での printf は禁止（数 ms ブロックし走行が乱れる）と教える
2. **LED**: 走行中のデバッグは printf より LED。「制御が効いた瞬間に点灯」など
   1bit 情報の可視化はマウスの基本技能
3. **SWD デバッガ（ST-Link）**: Nucleo に内蔵。ブレークポイントは走行中には使えない
   （止めた瞬間モータと制御が凍る）が、**Live Expressions** で走行中の変数
   （ad_l, pulse_l, mouse.x...）をリアルタイム監視できる。これは全員に体験させる価値がある
4. **map ファイル / Build Analyzer**: Flash 64KB / RAM 12KB の使用量を常に意識させる
5. 発展: UART ログを CSV で吐いて PC でグラフ化（センサ値と制御量の時系列）。
   壁制御のゲイン調整が「勘」から「観察」に変わる

## 3. 安全・運用上の注意（コードに現れない知見）

- **リポバッテリ（3S 11.1V）**: 低電圧監視は実装済み（`BATT_LOW_VOL`, LED4 点灯）だが、
  カウンタがリセットされないバグがある（01 §3.3）。充電・保管ルールは別途部内文書化を
- **ステッピングモータの脱調**: このコードの走行が乱れる原因の大半。加速しすぎ・
  電圧低下・機体重量増で起きる。「脱調とは何か、どう見分けるか」を課題プリントに書く
- **尻当て（set_position）**: 壁への押し付けで位置リセットする運用。パルス数
  `PULSE_SETPOS_BACK 300` は機体寸法依存なので、機体を作り替えたら要再調整
- **大会ルール由来の定数**: `HAL_Delay(2000)`（スタートで 2 秒静止, `search.c:93`）や
  5 分 5 走などはルールブック由来。ルール改定の確認を毎年度の恒例作業にする

## 4. パラメータ調整手順（現行コードの暗黙知の明文化）

配布時に README に載せるべき調整フロー:

1. **mode 7（センサチェック）**: 壁あり/なしで `ad_*` を読み、`WALL_BASE_*` を
   「壁あり最小値と壁なし最大値の中間」に設定
2. **mode 6 → test_run case 1（1 区画直進）**: 90mm ちょうど進むよう `PULSE_SEC_HALF` を調整
3. **test_run case 2/3/4（旋回×16 回 / ×8 回）**: 連続回転で誤差を積算させ、
   元の向きに戻るよう `PULSE_ROT_*` を調整（1 回では誤差が見えないための ×16）
4. **尻当て**: `PULSE_SETPOS_BACK/SET` を機体が壁に軽く当たって中央に来るよう調整
5. **壁制御**: 迷路の直線で `CTRL_BASE_*`（不感帯）と `CTRL_CONT`（ゲイン）を調整。
   振動する→ゲイン下げ、壁に寄る→不感帯下げ
6. 最後に mode 1（探索）→ mode 2（二次走行）

※ 現行の注意: **一度も mode 1 を完走せず mode 2 を実行するとフリーズする**
（EEPROM 未初期化、01 §3.3 参照）。改修で必ず直すべき点だが、それまでは運用で回避。

## 6. 改修プロジェクトの進め方（提案）

1. **フェーズ 0（済）**: git 管理開始、現状分析（本ドキュメント群）
2. **フェーズ 1**: 挙動を変えない安全な修正
   — 文字コード統一、既知バグ修正（01 §3.3）、README 作成、`.gitattributes` 等
   — 各修正を最小コミットで刻み、実機で回帰確認
   — テンプレート配布モデル（02 §5）では配布後の修正が各自のコピーに届かないため、
     このフェーズが**最優先**
3. **フェーズ 2**: 構造改修 — App/Platform 分離（04）、グローバル変数整理、
   `#ifdef MAIN_C_` 撲滅。**標準プログラムは恒久的に C のまま**とする
   - フェーズ 1 レビューからの持ち越し: `make_smap`/`make_route` が到達不能で
     打ち切られた場合に status を返し、探索走行を安全に中止できるようにする
     （現状はガードで無限ループは防ぐが、不正経路のまま走り続ける）
4. **フェーズ 3**: 教材化 — 穴あき化、課題プリント、シミュレータ（02）、
   Template repository 化・年度タグ運用の開始
5. **フェーズ 4（標準プログラム外）**: C++ 移行（03）は各自の個人リポジトリで
   挑戦する発展課題とし、標準プログラムには取り込まない
6. 毎フェーズ末に「新入生 1 人に触ってもらい詰まった箇所を記録する」
   ユーザーテストを挟むと教材の質が段違いになる

フェーズ 1 と 2 の間で一度、現行機体での完走動画とパラメータを記録しておくこと。
改修後の「同等に走るか」の判定基準になる。

## 7. ブランチ構成と実機検証待ちの作業（2026-07 時点）

| ブランチ | 内容 |
|---|---|
| `main` | 完全実装版（フェーズ1・2・シミュレータ・課題プリントまで反映） |
| `reference` | 模範解答として配布する版（現時点では main と同一） |
| `handout-draft` | 穴あき教材版（課題1〜5の実装箇所が TODO になっている。ビルドは通る） |

**実機検証がまだのため、以下の手順が残っている:**

1. `main` を実機で回帰確認する
   - Mode 7（センサ値と dif が生きた値で出るか）→ Mode 6（直進・旋回）→
     Mode 1 → Mode 2 の順
   - フェーズ2は構造改修であり挙動等価を意図しているが、
     割り込みタイミング依存の差は実機でしか分からない
2. 問題なければ `reference` を main に追随させ、`handout-draft` を配布版として
   仕上げる（穴あき状態でのビルド確認は済んでいる）
3. Template repository 化 → 年度タグ（例: `2027-handout`）を打って配布開始
