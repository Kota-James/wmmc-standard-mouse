# 教育向け再構成案 — 「配布して走る」から「作って走らせる」へ

## 0. 方針

現行コードの魅力（パラメータ調整だけで走る）と教育効果（自分で考えて実装する）は
トレードオフではなく、**層で分ければ両立できる**。

- **ハードウェア層（難しくて教育効果が薄い部分）は完成品として配布する。**
  タイマ設定・ADC・割り込み・Flash 書き込みは、STM32 と HAL の知識が必要で
  デバッグも困難。ここで新入生を溺れさせるのは得策ではない。
- **アルゴリズム層（紙とペンで考えられる部分）を新入生に実装させる。**
  壁判定・足立法・経路生成・制御則は、ハードなしでも考えられ、
  間違えても壊れず、動いたときの達成感が大きい。
- **「答え」は残す。** 現行実装（または模範解答）を別ブランチ/別ディレクトリに保持し、
  行き詰まった新入生がいつでも参照・比較できるようにする。

## 1. 提案するディレクトリ構成

```
Core/
  Inc/ Src/            … CubeMX 生成物 + ハードウェア層（配布側が管理、原則触らせない）
    hw_motor.c/h       … 旧 drive.c の基幹部分（drive_start/stop/set_dir, テーブル走行）
    hw_sensor.c/h      … 旧 sensor.c の ADC 部分 + interrupt.c のセンサ取得フェーズ
    hw_led_sw.c/h      … 旧 auxiliary.c
    hw_eeprom.c/h      … 旧 eeprom.c（有効性マーカー付きに改修）
App/                   … 新入生が編集する領域（HAL を一切 include しない）
  motion.c/h           … 半区画走行・旋回・尻当て（上位関数）
  wall.c/h             … 壁判定・基準値                      ★課題1
  control.c/h          … 壁沿い P 制御                        ★課題2
  maze.c/h             … マップ管理（write_map 等）           ★課題3
  solver.c/h           … 歩数マップ・経路生成（足立法）       ★課題4
  strategy.c/h         … 探索走行・二次走行・オートスタート   ★課題5
  params.h             … 機体ごとの調整パラメータ
Sim/                   … PC 上で App/maze.c, solver.c を動かすシミュレータ（後述）
docs/
  exercises/           … 課題プリント（課題ごとに 1 ファイル）
```

ポイント:

- **App/ は HAL 非依存**にする。`hw_*.h` が提供する小さな API
  （`hw_motor_run(pulses)`, `hw_sensor_get(SENSOR_L)`, `hw_led_set(...)` 等）だけを使う。
  これにより App/ のコードはそのまま PC でコンパイルでき（→シミュレータ）、
  将来のマイコン変更（[04_マイコン移植ガイド.md](04_マイコン移植ガイド.md)）にも効く。
- グローバル変数の `#ifdef MAIN_C_` パターンは全廃し、
  「.c で定義・.h で extern」または引数渡しに統一する。
  迷路状態は `maze_t` / `mouse_state_t` 構造体にまとめ、関数に渡す形にする
  （「状態はどこにあるか」を新入生が意識できる）。

## 2. 新入生に実装させる部分（穴あきコード化の具体案)

「全部白紙」は挫折する。**関数のシグネチャ・コメント・テスト（期待動作）は与え、
中身だけを TODO にする**のが要点。現行コードの以下を穴あきにする。

### 課題1: 壁判定（現 `sensor.c:141-161` `get_wall_info`）
- 与えるもの: `ad_l/ad_r/ad_fl/ad_fr` が自動更新される仕組み、センサチェックモード
- 書かせるもの: 閾値比較で `wall_info` を作る処理
- 学べること: AD 値の物理的意味、閾値の決め方、ビット演算
- 難易度: ★（最初の 1 週間で全員通過させる）

### 課題2: 壁沿い制御（現 `interrupt.c:150-175` の P 制御ブロック）
- 与えるもの: `dif_l/dif_r` の計算、制御量 `dl/dr` がモータ周期に反映される仕組み
- 書かせるもの: 偏差から制御量を決める式（まず P、発展で PD）
- 学べること: フィードバック制御の初歩、ゲイン調整の体感
- 注意: ISR 内で動くコードなので、「重い処理を書かない」ルールを課題文に明記する

### 課題3: マップ記録（現 `search.c:264-350` `map_Init`/`write_map`）
- 与えるもの: 座標系・壁ビット割り当ての図解、`turn_dir`/`adv_pos`
- 書かせるもの: 壁情報を自機方位で補正してマップに書く処理、隣接区画への反映
- 学べること: 座標変換、ビットシフト、境界条件
- **シミュレータで検証させる**（実機不要。printf でマップを描画する `maze_print()` を配布）

### 課題4: 足立法（現 `search.c:370-534` `make_smap`/`make_route`）
- 与えるもの: 歩数マップの概念説明（docs/exercises 内で図解）、迷路データ数十本
- 書かせるもの: 歩数マップ生成と経路導出。まず現行方式（全域走査）でよい
- 発展課題: キューを使った BFS 化（計測して速度差を体感させる）、
  未探索区画の扱い（楽観/悲観）の違いが探索効率に与える影響の考察
- 学べること: グラフ探索、計算量、データ構造
- **これが本教材の山場。** 実機なしで完結するので入部直後の座学期間にも使える

### 課題5: 走行戦略（現 `main.c:158-224` + `search.c:42-213`）
- 与えるもの: `motion.h` の上位 API（`go_half_accel()`, `turn_right()`, `back_to_center()` 等）
- 書かせるもの: 探索走行のメインループ（壁を見る→マップ更新→経路再計算→動く）、
  帰り探索、二次走行、5 分 5 走を意識したオートスタートモード（現 mode 3 の空欄）
- 学べること: 状態機械、競技ルールの理解、運用設計

### 配布側で完成させておく部分（触らせない）
- タイマ・ADC・GPIO の初期化と ISR の骨格（interrupt.c のフェーズ巡回構造）
- 加減速テーブル走行（driveA/D/U/C 相当）
- EEPROM 読み書き（有効性マーカーを追加した改良版）
- モード選択 UI・printf 環境

## 3. カリキュラム（例: 4〜7 月の週次）

| 週 | 内容 | 使う課題 |
|---|---|---|
| 1 | 開発環境構築、L チカ、スイッチ、printf | — |
| 2 | センサ値の観察、課題1（壁判定）、閾値調整 | ★1 |
| 3 | テスト走行モードで直進・旋回のパラメータ調整 | — |
| 4 | 課題2（壁沿い制御）、ゲイン調整大会 | ★2 |
| 5-6 | シミュレータで課題3・課題4（マップ・足立法） | ★3,4 |
| 7 | 実機に載せて探索走行を完成 | ★5 |
| 8+ | 二次走行、オートスタート、各自の改良（→大会へ） | 発展 |

各課題の合格条件を明文化する（例: 課題4は「配布迷路 10 本全てで最短歩数経路を出力」）。
これは後述のシミュレータがあれば**自動採点**にできる。

## 4. PC シミュレータ（強く推奨する追加投資）

App/ を HAL 非依存にすると、`maze.c`/`solver.c` は gcc でそのままビルドできる。
以下だけ用意すれば十分（数百行、上級生の C++ 課題にしてもよい）:

- 迷路ファイル読み込み（公開されている maze データセットが利用可能。
  GitHub の `micromouseonline/mazefiles` に大会迷路が多数ある）
- 「仮想マウス」: `adv_pos`/`turn_dir` 相当と、現在区画の壁だけを返す関数
  （＝実機のセンサと同じ情報制約を再現する）
- 歩数マップ・経路のターミナル描画

効果: 実機の台数が部員数より少なくても全員が並行して課題を進められる。
デバッガで止めながらアルゴリズムを追える。「実機で動かない」原因の切り分けが
「アルゴリズムか、ハードか」で二分できる。

## 5. Git 運用（教育の一部として）

- `main`: 配布用の穴あき教材コード
- `reference`: 模範解答（現行コード相当の完動版）。新入生には最後に開示
- 新入生は各自フォーク（または `student/<名前>` ブランチ）で課題を進め、
  課題ごとに Pull Request を出し**上級生がコードレビューする**。
  レビュー文化そのものが実務的教育になる
- タグで年度を管理（`2026-handout` 等）し、翌年の教材更新を差分で追えるようにする

## 6. 教材品質のための下準備（改修時にやるべきこと）

1. 文字コードを UTF-8 / 改行 LF に統一し、`.gitattributes` と `.editorconfig` を置く
   （現 `main.c` の文字化けコメントは書き直しが必要）
2. マジックナンバーを enum / #define に置換（方向、壁ビット、モード番号）
3. `min`/`max` マクロの括弧修正、`__io_putchar` の型修正などの既知バグ潰し
   （[01_現状コード分析.md](01_現状コード分析.md) §3.3 の一覧）
4. `params.h` の各値に**物理的根拠**（車輪径・ステップ角・区画 90mm からの計算式）を
   コメントで併記。加減速テーブルの生成スクリプト（Excel の代わりに Python 等）を
   リポジトリに同梱する
5. README を書く（機体仕様、ピン割り当て表、ビルド手順、調整手順、課題の進め方）

## 7. やり過ぎないための注意

- **抽象化のし過ぎは初心者に毒。** 層は「hw_ / App/」の 2 段で止める。
  コールバック・関数ポインタの多用は避け、素直な関数呼び出しで組む。
- ブロッキング走行（`while(pulse < dist);`）は教育段階ではむしろ分かりやすいので
  当面維持してよい。ノンブロッキング化・RTOS 導入は上級生の発展課題とする。
- 現行の詳細コメント文化は維持する。ただし「コードの直訳コメント」より
  「なぜそうするか」を書く方針に改める。
