# 現状コード分析 — NucleoMouse2023（改修前のアーカイブ版。現 wmmc-standard-mouse）

対象: `Core/Src/*.c`, `Core/Inc/*.h`（CubeMX 生成部を除くユーザーコード約 3,300 行）
MCU: STM32F303K8（Nucleo-32, Cortex-M4F 64MHz, Flash 64KB / RAM 12KB）
機体: ステッピングモータ 2 輪 + 赤外線壁センサ 4 個（左・右・前左・前右）+ バッテリ電圧監視

---

## 1. 全体構成

### 1.1 モジュール構成

| ファイル | 責務 | 行数 |
|---|---|---|
| `main.c` | CubeMX 生成の初期化 + モード選択ループ（UI 兼シナリオ） | 798 |
| `drive.c` | 走行系。上位関数（半区画走行・旋回・尻当て）と基幹関数（driveA/D/U/C） | 481 |
| `interrupt.c` | タイマ割り込み。ステッパのパルス生成（TIM16/17）とセンサ・制御タスク（TIM6） | 197 |
| `sensor.c` | ADC 読み取り、壁判定、制御基準値取得 | 161 |
| `search.c` | 足立法探索。マップ管理・歩数マップ・経路生成・EEPROM 保存 | 568 |
| `auxiliary.c` | LED、スイッチによるモード選択、printf 用 `__io_putchar` | 92 |
| `eeprom.c` | 内蔵 Flash の Page 31 を EEPROM 代わりに使う読み書き | 92 |
| `params.h` | 調整パラメータ（走行パルス数・閾値・ゴール座標） | 64 |
| `table.h` | Excel で事前計算した加減速テーブル（ARR 値の CSV、300 要素） | 301 |
| `global.h` | フラグ共用体 `MF` の定義 + 全ヘッダの一括 include | 70 |

### 1.2 動作の仕組み（データフロー）

```
[TIM16 割込 (左モータ)] ──┐  パルスごとに pulse_l++ し、加減速テーブル table[t_cnt] から
[TIM17 割込 (右モータ)] ──┤  次周期(ARR)を設定。壁制御量 dl/dr を周期に加算
                          │
[TIM6 割込 4ms 周期] ─────┤  3 フェーズ巡回 (tp=0,1,2):
   0: 横センサ AD 取得     │    LED 点灯→15µs 待ち→ADC ポーリング→消灯
   1: 前センサ + 電圧取得  │
   2: 壁 P 制御 → dl/dr    │
                          ▼
[main ループ] モード選択 → searchB() → 足立法で make_smap/make_route →
              route[] に従い drive.c の上位関数を呼ぶ →
              driveX() 内で while(pulse < dist); とビジーウェイト
```

- 走行指令は**全てブロッキング**。`driveA(dist)` は割り込みが進める `pulse_l/r` を
  メインループ側でポーリングして待つ（`drive.c:176`）。
- 速度制御は**テーブル駆動**。加速度計算は Excel で行い、割り込み間隔（ARR 値）の列を
  `table.h` に貼り付ける方式（`drive.h:46`, `interrupt.c:61`）。
- 迷路は `map[16][16]` の各バイトに北東南西の壁を 1bit ずつ、
  下位 4bit = 一次走行用（未探索は壁なし扱い）、上位 4bit = 二次走行用（未探索は壁あり扱い）
  として二重に持つ（`search.h:15-27`）。
- 壁情報・経路の要素は `0x88=前, 0x44=右, 0x22=後/U턴, 0x11=左` という
  「上位・下位ニブルに同じパターンを複製した」符号化で統一されており、
  `wall_info & route[r_cnt]` の 1 演算で「次の進路に壁があるか」を判定できる（`search.c:251`）。

## 2. 良い点（改修後も残すべき価値）

1. **配布してパラメータ調整だけで完走できる完成度**。ハードが動く「正解」が
   手元にあることは初心者の安心材料であり、改修後もリファレンス実装として保持すべき。
2. **コメント量が非常に多い**。ほぼ全行に日本語コメントがあり、行き詰まったときに
   コードだけで自習できる。共用体ビットフィールド（`global.h:20-49`）や走行の仕組み
   （`interrupt.c:16-32`）など、仕組みの解説コメントも良質。
3. **関数の階層設計が明確**。`drive.c` は「上位関数（half_sectionA 等）／基幹関数（driveA/D/U/C）」の
   2 層に整理され、`search.c` からはハードを意識せず上位関数を呼ぶだけでよい。
4. **テーブル駆動の加減速**はステッパ制御の定石であり、設計自体は正しい。
5. **モード選択 UI（`select_mode`）とセンサチェックモード（mode 7）**など、
   大会現場での運用に必要な足回りが揃っている。
6. **`wall_info`/`route` の共通符号化**は巧妙で、理解できれば美しい設計。
   （ただし後述の通り初見には難解で、教育上はトレードオフがある）
7. RAM 12KB / Flash 64KB という制約に対し、`map`/`smap`/`route` 合わせて 1KB 未満と
   メモリ設計は健全。

## 3. 問題点

### 3.1 構造上の問題（最重要）

#### (a) `#ifdef MAIN_C_` によるヘッダ内グローバル変数「定義」
`drive.h:44-60`, `sensor.h:16-30`, `search.h:37-69`, `global.h:51-57` の全てで

```c
#ifdef MAIN_C_
  volatile int16_t t_cnt_l, t_cnt_r;   // main.c から include されたときだけ「定義」になる
#else
  extern volatile int16_t t_cnt_l, t_cnt_r;
#endif
```

というパターンを使っている。C の標準的な作法（.c で定義し .h で extern 宣言）から
外れており、以下の実害がある。

- 変数の実体がどこにあるかコードから読み取れない（初心者が最初に混乱する箇所）。
- `main.c` が `#define MAIN_C_` を include より前に書くことが暗黙の前提で、崩すとリンクエラー。
- 全変数が全モジュールから見えるため、**どの関数がどの状態を読み書きするかが追えない**。
  例えば `wall_info` は `sensor.c` が書き、`search.c` と `main.c` が読む。

#### (b) `global.h` による全ヘッダ一括 include
`global.h:59-66` が全ヘッダを include し、全 .c が `global.h` だけを include する。
モジュール間の依存関係が完全に不可視になっており、「sensor は drive に依存しない」
といった設計情報が失われている。ヘッダの並び順にも暗黙の依存がある
（`auxiliary.h` の `min`/`max` マクロを `interrupt.c` が使う等）。

#### (c) `table.h` が「ヘッダ」ではなく配列初期化子の断片
`drive.h:46-48` で `const uint16_t table[] = { #include "table.h" };` としており、
`table.h` の中身は CSV（`file` コマンドでも C ソースと認識されない）。
Excel での生成手順がリポジトリに残っておらず、**加速度・最高速度を変えたくても
再生成方法が分からない**。物理量（車輪径、ステップ角、区画 90mm との対応）も
どこにも書かれていない。`PULSE_SEC_HALF 218` 等（`params.h:18-23`）の根拠も同様。

#### (d) main.c のモード 1 とモード 2 がほぼ完全な重複
`main.c:158-192` と `main.c:194-224` は `MF.FLAG.SCND` の値以外同一。
仕様変更時に片方だけ直す事故の温床。同様に `searchA`/`searchB`（`search.c:42-213`）も
大部分が重複している（searchA は main から呼ばれていない死にコードでもある）。

### 3.2 割り込み設計の問題

#### (e) 全割り込みが同一優先度で、センサ ISR が長時間ブロックする
`stm32f3xx_hal_msp.c:226-255` で TIM6/TIM16/TIM17 全てが優先度 (0,0)。
TIM6 の ISR（`interrupt.c:98-182`）は LED 点灯 → **15µs ビジーウェイト** →
ADC ポーリング×2〜3ch を ISR 内で行うため、数十 µs 以上走る。
同一優先度なのでこの間ステッパの TIM16/17 割り込みが遅延し、
高速走行時のパルス周期にジッタが乗る。現状の速度域では顕在化しにくいが、
「ISR は最短で抜ける」「優先度を設計する」という基本に反しており、教材としても悪い見本。

#### (f) ビジーウェイトによる完全ブロッキング走行
`driveA/D/U/C` の `while((pulse_l < dist) || (pulse_r < dist));`（`drive.c:176` ほか）は
走行中メインループを占有する。動作としては成立するが、
走行中に別処理（ログ送信、スイッチ監視、緊急停止）を挟む余地がない。

### 3.3 バグ・コメント不一致（具体箇所）

| 箇所 | 内容 |
|---|---|
| `auxiliary.h:13-14` | `min`/`max` マクロに外側の括弧がない。`2 * min(a,b)` のような式で誤展開する。二重評価の問題もある |
| `auxiliary.c:85-92` | `__io_putchar` で `int` 変数のアドレスを `uint8_t*` 引数に渡している（リトルエンディアン依存・要警告確認）。タイムアウト 1ms のため大量出力時に文字が落ち得る |
| `search.c:156-181` | 180 度回転時の壁当て直し。コメントは「前壁と**左壁**」だが条件は `ad_r`（右壁）を見ている（動作は正しく、コメントが誤り）。さらに 1 つ目の分岐は閾値 `×1.5` なのに 2 つ目の `ad_l` は係数なしで非対称 |
| `drive.c:117-125` | `rotate_180` は `ROTATE_R` を設定しているのにコメントが「左に旋回」 |
| `sensor.c:123-132` | `get_base` の戻り値 `res` は常に 1。「理想的な値を取得できたか」の判定が未実装 |
| `interrupt.c:130-139` | 低電圧判定の `low_vol_count` が回復時にリセットされない。生涯累計 1000 回瞬間的に下回ると以後フラグが立ちっぱなしになる |
| `interrupt.c:150-175` | `dif_l/dif_r` は `MF.FLAG.CTRL` が立っているときしか更新されないため、センサチェックモード（mode 7, `main.c:269`）で表示される `dif_l/dif_r` は常に 0（または前回走行の残骸）で、調整の役に立たない |
| `search.c:542-552` | `store_map_in_eeprom` が `eeprom_write_halfword` の戻り値（HAL_StatusTypeDef）を全て無視。書き込み失敗しても気づけない |
| `eeprom.c` 全般 | 有効性マーカーがない。**一度も探索せずに mode 2（二次走行）を実行すると、消去済み Flash の 0xFF がマップとして読み込まれ、全区画が全壁扱いになって `make_smap` が無限ループ（フリーズ）する** |
| `search.c:453,465-531` | `route[256]` に対しループ変数 `i` の上限チェックがない。マップ整合性が崩れた場合バッファオーバーラン |
| `drive.c:196` | `driveD` の減速開始距離を左輪の `t_cnt_l` だけで計算（左右非対称）。また ISR が書き換える volatile 変数を非アトミックに読む |
| `drive.c:414-481` | `test_run` は `while(1)` で抜けられず、末尾の `drive_disable_motor()` は到達不能。メインメニューに戻れない |

### 3.4 可読性・保守性の問題

- **マジックナンバーの多用**: 方向 `0x00/0x01/0x02/0x03`、壁 `0x88/0x44/0x22/0x11`、
  `drive_set_dir` の `0x00/0x01/0x10/0x11`、`DIR_TURN_L90 0xff`（uint8_t のラップアラウンドを
  利用した -1）など。enum や名前付き定数がなく、`search.c` の読解に暗号解読が必要。
- **迷路サイズ 16 のハードコード**: `search.c` 中に `16`, `15`, `0xff` が散在。
  クラシック競技（16×16）以外への変更やハーフサイズ（32×32）対応が困難。
  ゴールも 1 区画指定で、公式ルールの 2×2 ゴール領域に対応していない。
- **文字コード・改行コードの混在**: `main.c` は過去の Shift-JIS→UTF-8 変換に失敗しており
  コメントが文字化けしている（U+FFFD が多数残存）。CRLF/LF も混在。
  また一部ファイルは clang-format が日本語コメントを巻き込んで
  `route\n[r_cnt++]`（`search.c:61-63`）のような不自然な改行を生んでいる。
- **`Error_Handler` が空**（`main.c:773-780`）: HAL 初期化失敗が黙殺される。
- **README・回路図・調整手順書がリポジトリにない**: パラメータの意味は
  コメント頼み。ハード（センサ配置、モータドライバ SLA7078 の結線）はコードから逆算するしかない。

### 3.5 アルゴリズム面の限界（教材ネタとして有用）

- `make_smap`（`search.c:370-436`）は「歩数 n の区画を全域走査して n+1 を書く」方式で、
  最悪 O(歩数 × 256) の全域再走査。キュー（リングバッファ）を使う典型的な
  幅優先探索に置き換えると桁違いに速くなる。**これ自体が新入生の格好の課題**。
- 探索は足立法のみ、二次走行も「上位ニブルのマップで同じ探索走行」であり、
  最短経路のスラローム走行・斜め走行は未実装。上級生の拡張余地として大きい。
- 壁制御は P 制御のみ（`interrupt.c:150-175`）。制御工学の導入教材として
  PD/PI 化の課題に発展させられる。

## 4. まとめ

| 観点 | 評価 |
|---|---|
| 動くこと・完成度 | ◎ 配布即走行可能。リファレンスとして価値が高い |
| コメント・自習性 | ○ 量は十分。ただし文字化け・コメントと実装の不一致が信頼を損なう |
| モジュール構造 | △ ファイル分割は妥当だが、グローバル変数と global.h が依存を破壊している |
| 割り込み設計 | △ 動くが優先度未設計・ISR 長すぎ。教材として悪い癖がつく |
| 堅牢性 | × エラー処理ほぼなし。未探索での二次走行フリーズなど地雷あり |
| 拡張性 | × 迷路サイズ・MCU・アルゴリズムの変更がいずれも高コスト |

このコードは「完成品の配布物」としては優秀だが、「新入生が中身を理解し、
自分の手で育てる教材」としては密結合と暗黙知が障壁になっている。
具体的な再構成案は [02_教育向け再構成案.md](02_教育向け再構成案.md) を参照。
