# マイコン移植ガイド — STM 内で MCU を変えても死なないコードの書き方

想定シナリオ: F303K8（Nucleo-32）から F4/G4/L4 系や別パッケージへの変更、
Nucleo からオリジナル基板への移行、CubeMX プロジェクトの作り直し。

## 0. 現状の移植コスト

現行コードは HAL 呼び出し（`HAL_GPIO_WritePin`, `__HAL_TIM_SET_AUTORELOAD`,
`hadc1`/`htim16` などのハンドル）が **drive.c / sensor.c / interrupt.c / search.c /
main.c 全てに直接埋まっている**。MCU を変えると:

- タイマ番号が変わる（F303 の TIM16/17 が対象 MCU にあるとは限らない）→ 全ファイル修正
- ADC チャンネル割り当てが変わる → sensor.c 修正
- Flash 構造が変わる（後述）→ eeprom.c 全面書き換え
- ピン名マクロ（`main.h` の `LED1_Pin` 等）は CubeMX が再生成するので比較的無事

つまり「.ioc を作り直す」だけでは済まず、アプリ全体に手が入る。これを
**「書き換えるのは 1 ディレクトリだけ」**にするのが本ガイドの目標。

## 1. 基本原則: アプリとハードの境界に「自分の API」を挟む

```
┌───────────────────────────────┐
│ App/ （移植時に無修正）                          │
│   solver.c  maze.c  strategy.c  motion.c       │
│      ↓ 呼ぶのは自分たちで決めた API だけ          │
├───────────────────────────────┤
│ Platform/xxx/ （MCU ごとに 1 セット書く）        │
│   hw_motor.c  hw_sensor.c  hw_eeprom.c  ...    │
│      ↓ ここだけが HAL / ハンドルを知っている      │
├───────────────────────────────┤
│ CubeMX 生成物（.ioc から自動生成、手で書かない）   │
└───────────────────────────────┘
```

### 1.1 境界 API（ヘッダ）は 1 セットに固定する

例（C の場合。C++ ならクラスのインターフェースで同じことをする）:

```c
/* hw_motor.h — どの MCU でも同じファイルを使う */
typedef enum { MOTOR_L, MOTOR_R } motor_id_t;
void hw_motor_init(void);
void hw_motor_enable(bool on);                    /* 励磁 */
void hw_motor_set_dir(motor_id_t m, bool fwd);
void hw_motor_start(void);                        /* パルス生成開始 */
void hw_motor_stop(void);
void hw_motor_set_interval(motor_id_t m, uint16_t us); /* 次パルスまでの時間 */
uint16_t hw_motor_pulse_count(motor_id_t m);
void hw_motor_on_pulse(void (*cb)(motor_id_t));   /* 割り込みからの通知 */
```

- 実装ファイル `Platform/f303k8/hw_motor.c` の中だけに `htim16` や
  `__HAL_TIM_SET_AUTORELOAD` を書く。**App/ に `stm32f3xx_hal.h` を include させない**
  （include したら負け、というルールが最も簡単で検査もしやすい）
- 移植先ごとに `Platform/g431kb/hw_motor.c` を書き足す。切り替えはビルド対象の
  ディレクトリ選択（CubeIDE なら Source Location / Exclude from build）で行う。
  関数ポインタや #ifdef の分岐より、**リンク時に差し替える**方が単純で実行コストゼロ

### 1.2 単位は「物理量」で渡す

現行 API はパルス数・ARR 生値・AD 生値がむき出しで、モータや ADC 分解能を変えると
呼び出し側の数値が全て狂う。境界 API では

- 距離: mm、角度: 度、時間: µs/ms、電圧: mV

を使い、パルス⇔mm の換算（車輪径・ステップ角・分周比）は Platform 側の定数に閉じ込める。
`params.h` の `PULSE_SEC_HALF 218` のような「機体と MCU の情報が混ざった数」を撲滅できる。

## 2. CubeMX / CubeIDE との付き合い方

1. **.ioc（CubeMX 設定）は Platform の一部**と考える。MCU ごとにプロジェクト
   （.ioc + 生成物）を分け、App/ を共通ソースとして両プロジェクトから参照する
   （CubeIDE の Linked Folder、または git submodule / 単一リポジトリ内の共有ディレクトリ）
2. **CubeMX 生成ファイルには原則手書きコードを置かない**。現行コードは main.c の
   USER CODE セクションにシナリオ全体が書かれているが、これを
   `app_main()` 呼び出し 1 行に減らす。USER CODE セクションは再生成に耐えるとはいえ、
   diff が汚れ、MCU 変更時に「移植すべき手書き部分」の発見を難しくする
3. ピン割り当ては CubeMX 上で**必ずユーザーラベル**（LED1, IR_SIDE, CLOCK_L 等）を
   付ける。現行はこれができており（`main.h:72-121`）、移植時もラベル名を揃えれば
   GPIO 系コードは Platform 内で無修正になる。この規約は明文化して維持する
4. クロック設定変更に備え、タイマ分周は「タイマ入力クロック→1MHz」を導出する形で
   書く（現行の `Prescaler = 64-1` のような即値は 64MHz 前提の暗黙知。
   `(SystemCoreClock / 1000000) - 1` などで意図を残す）

## 3. MCU 間で特に差が出る箇所（要注意リスト）

| 機能 | F303K8（現行） | 移植時の罠 |
|---|---|---|
| Flash の EEPROM 代用 | 2KB ページ、halfword 書込、`FLASH_TYPEERASE_PAGES` | F4 は不均一「セクタ」（16KB〜128KB）で API も別物。G4/L4 は 2KB/4KB ページだが**doubleword(64bit) 書込のみ**。`eeprom.c` は MCU ごとに書き直し前提の設計にし、`hw_eeprom.h`（read/write/erase をオフセット指定）の裏に隠す |
| EEPROM 開始アドレス | `0x0800F800`（最終ページ直書き） | Flash 容量が変わると即死。**リンカスクリプトでセクションを予約**し、シンボル経由でアドレスを得る方式にすると安全 |
| タイマ | TIM6/16/17 | 型番によって存在するタイマ・IRQ 名（`TIM1_UP_TIM16_IRQn` 等の合流割り込み）が違う。ISR 名も Platform 側の stm32xxx_it.c に閉じる |
| ADC | F3 は ADC1/2 独立、ch 割り当て固定 | G4/L4 で校正手順（`HAL_ADCEx_Calibration_Start`）がほぼ必須。サンプリング時間の定数名も系列で異なる |
| printf リターゲット | `__io_putchar`（newlib-nano） | 同じ newlib なら共通。ただし float printf の有効化フラグはプロジェクト設定なので .ioc 再作成時に忘れやすい |
| HAL ヘッダ名 | `stm32f3xx_hal.h` | App/ が include していなければ無関係になる（＝本ガイドの原則が効く） |

## 4. 移植を「事件」にしないための日常の規律

- **HAL 依存の棚卸しを自動化**: `grep -rl "stm32f3xx\|HAL_\|htim\|hadc" App/` が
  空であることを CI（または上級生レビュー）でチェックする
- 新しい機能を書くとき「これは App か Platform か」を最初に決める。
  迷ったら「PC のシミュレータでも動くべきか？」で判定する
  （動くべき → App、ハードがないと意味がない → Platform）
- Platform API を変更するときは全 Platform 実装を同時に更新する
  （実装が 1 つしかない期間も、この意識だけで API の質が上がる）
- 移植作業自体を教材化する: 「hw_motor.h を満たす実装を G431 で書け」は
  上級生の実践課題としてちょうど良い粒度

## 5. 適用状況（フェーズ2で実装済み）

[02_教育向け再構成案.md](02_教育向け再構成案.md) の再構成と同時に適用した。
実際のディレクトリは CubeIDE の制約（.cproject を変更しない）を考慮して
`Core/Src/app/`（アプリ層）と `Core/Src/platform/`（F303K8 実装）とした。

1. ✅ app / platform にファイルを振り分け、境界 API（`Core/Inc/hw/*.h`）を定義
2. ✅ app 側から HAL include を追放（`grep -r "HAL_\|stm32f3" Core/Src/app Core/Inc/app Core/Inc/hw`
   が空であることが検収条件。CI に組み込むとよい）
3. ✅ ISR 共有変数（pulse, t_cnt, ad_*, steering）は platform 内部の volatile static とし、
   取得関数経由に変更
4. ✅ eeprom はオフセット指定 API に変更（リンカセクション方式への変更は
   マイコン移植の際に platform 側だけで行えばよい）
5. ⬜ 2 つ目の platform 追加は実際にマイコンを変える時点で（原則の検証を兼ねる）

残課題: 割り込みから app 層を呼ぶ制御フック（`hw/app_hooks.h` の `app_control_tick`）は
リンク時結合のため、app 側が実装を忘れるとリンクエラーになる（それが検出手段でもある）。

この構成は [03_Cpp移行ガイド.md](03_Cpp移行ガイド.md) のクラス設計とも直交しない。
C++ 化する場合は platform 実装をクラスの中に入れるだけで、境界の考え方は同一。
